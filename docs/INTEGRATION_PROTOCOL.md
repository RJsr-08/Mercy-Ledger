# Person D — Master Integration Protocol

## Ownership and merging

Person D owns the master project. A, B and C must work in separate copies and return only the files named in their current priority prompt. Do not replace the entire master directory with a teammate's project folder.

Before copying files, make a backup of the master folder (or commit it to version control). Copy only named deliverables. Inspect every unexpected change and reject unrelated edits.

## Priority 1 merge order

1. `simulator.py` from A.
2. `triage.py`, `sla.py`, `impact.py` from B.
3. `grievance.py`, `orders.py` from C.
4. `static/index.html` from D's own frontend work.
5. Run `python check_my_work.py all`. Fix real problems before considering further features.
6. Only when all checks pass, run `python make_sample_data.py`, then start the server and test all presets. Run `python benchmark.py` only if its guard passes; report the measured result without unsupported speed claims.

## Priority 2 merge order

Merge new standalone modules from A/B/C without overwriting the core modules. D owns any approved changes to `app.py` or the interface. Run the new unit tests and `python check_my_work.py all` again. If P1 regresses, revert the P2 changes and repair them before proceeding.

Expected optional files:
- A: `invariants.py`, `stress_test.py`, `test_priority2_invariants.py`
- B: `review_flags.py`, `test_priority2_review_flags.py`
- C: `victim_explainer.py`, `test_priority2_explainer.py`
- D: `static/index.html`, `app.py` only if needed for new endpoints, and `test_priority2_api.py` if added.

## Priority 3 merge order

Only proceed after Priority 2 passes and only if time remains. Merge:
- A: `chain.py`, `test_priority3_chain.py`
- B: `sensitivity.py`, `test_priority3_sensitivity.py`
- C: `audit_integrity.py`, `test_priority3_audit_integrity.py`
- D: `static/index.html`, `app.py` only if needed for the optional endpoints.

Priority 3 must be reversible. If any module cannot pass its tests, omit that feature and keep Priority 1/2 stable.

## Evidence required before a feature is accepted

For every module, retain:
1. The complete file.
2. The exact command executed.
3. The actual command output.
4. At least one edge case or negative test.
5. Any remaining limitation in plain English.

A green badge, benchmark number, test count or output must be generated by a real run. Never hardcode success counts.
